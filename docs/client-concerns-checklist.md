# Loanstar client concerns checklist

Use this checklist to assess the ten concerns raised in the attached screenshots. Severity and effort are provisional. Effort is in working days for one person to check the concern, make any needed change, and test it. The screenshots and messages are the source for this checklist. The live behavior and causes are still to be verified.

Items are grouped by severity and ordered by the low end of the estimate within each group. The client identified the release-date concerns as their biggest priority.

## Major

- [x] **4. CIG cannot edit after a direct Committee return** — **½–1 day**
  - **Context:** The client says that when Committee sends an application directly back to CIG, the information stays locked for editing. (Image 2)
  - **Check:** Return a test application from Committee directly to CIG and see whether CIG can edit the information that needs correcting.
  - **Assessment notes:** Audited and **reproduced: real bug, Major.** On dev application AN300024, Committee returned the file to CIG (status For Revision). CIG then saw every field disabled (field completeness, borrower interview, crewing manager, finding), a banner "Submitted to Committee — view only. Edits are locked.", and only a "Revision complete" button. A direct save attempt returned 403 "Application is not in verification stage" and changed nothing. Root cause: the CIG API sets `editable` only when status is `for_verification` (`src/app/api/cig/applications/[id]/route.ts:400`), the save guard requires the same (`src/lib/cig/queue-guards.ts:24`), and the database write policies for CIG verification, checks and borrower edit also require `for_verification`. A Committee return sets status `for_revision`, which CSA treats as editable (`src/lib/csa/status.ts`) but CIG does not. The CIG workspace text already tells staff to complete the requested updates and mark revision complete, which they cannot do. Likely fix: allow CIG edits when status is `for_revision` and the open return notice is routed to CIG, in the page flag, the save guard and the database write policies; this needs a migration, so the ½–1 day estimate may be low. Not yet checked: the CSA-route return (#5 covers it), what "Revision complete" does after the fix, and whether the borrower-edit policy should also open. **Fixed on staging, uncommitted.** Added `assertCigEditStage` and `isCigEditableStage` (`src/lib/cig/edit-stage.ts`, `src/lib/cig/queue-guards.ts`), used by the CIG save route and the checks route, and the `editable` flag now follows the same rule. New migration `supabase/migrations/20261116120000_cig_edit_during_cig_revisit.sql` widens `verifications_write`, `checks_recorded_cig_write`, `borrowers_cig_update` and `applications_cig_borrower_edit` to also accept `for_revision` with an open CIG-routed notice; applied to the staging project only (recorded there as `20261115191347`). Forward, return, cancel and callback keep the verification-only guard. Verified on AN300024: after the return CIG fields and Save buttons are enabled, borrower-review notes, a crewing change and a check pass all persist; "Revision complete" moves the file to For Approval and CIG is locked again (direct save returns 403); a return routed to CSA keeps CIG locked (403). CIG unit tests: 172 pass. Not verified: forward, return, cancel and callback on a normal verification file in the browser (covered only by a unit test), and an unlocked-page screenshot. Production still needs separate approval and the same migration. Plan: `docs/revision-plans/fix-cig-edit-after-committee-return-plan.md`.

- [x] **1. Record a loan using its actual past release date** — **1–2 days**
  - **Context:** Staff are working with both manual records and Loanstar. The client says some loans are released manually before staff enter them in the system. They want to enter the actual release date because the repayment schedule depends on it. (Images 2–3)
  - **Check:** See whether staff can record a loan with a past release date and whether the repayment schedule uses that date.
  - **Assessment notes:** Audited, **fixed and verified on staging (uncommitted, no database change).** Audit: for every loan type except Daily Interest, the release date was set to today when CSA clicked Compute (`src/lib/csa/computation.ts`), the first payment date and schedule counted from it, and LRA then overwrote it with the click date at release (`src/lib/lra/release-service.ts`), so the PDC check schedule (built before release) and the AR billing schedule (built after) could use different dates. Only Daily Interest had a Release date field. The client's Excel has a hand-typed "Released Date" (`SEAMAN (offset)!F19`) with a derived "Payment Start". Decisions (confirmed with the user 2026-11-16): field for all loan types, prefilled with today and editable, no date limits, set before Compute (changing it means computing again and signing the new computation again, in-branch signing still available), the date is kept at release, and LRA access to the calculator is a separate task. Fix: a Release date field in the calculator for every loan type (`ComputationPanel.tsx`, prefilled with the local date, saved date restored on reload), sent with every Compute and validated as YYYY-MM-DD (CSA compute route, Committee override route); read and stored as a local calendar date (`computation.ts`, which also fixes the old default that showed yesterday between midnight and 8 AM); the release-time overwrite removed; and Committee's adjust/override (`src/lib/negotiation/service.ts`) now keeps the date for every loan type instead of resetting it to today. Verified in the browser: field shows and is prefilled; the Excel case (release 2026-07-20, 2 add-on months, due day 15) gives first payment 2026-09-15; past (2026-11-06 gives 2027-01-15) and future (2026-12-05 gives 2027-02-15) dates work; the date persists after reload and the new computation shows "Awaiting signature"; Committee set 2026-11-30 and it saved, and a second recalculate kept it. Computation, csa, lra and negotiation tests: 537 pass. Not verified in the browser: Daily Interest (existing tests cover it), the LRA release step (source-text test only; no dummy file at LRA), and the origination-discount preview, which still uses the saved date until recompute. Open points: reports and the dashboard now show the entered release date instead of the LRA click date; concern #2 (paperwork for a future release) should be mostly covered by this field but is not confirmed; LRA calculator access is tracked separately below. Plan: `docs/revision-plans/fix-manual-release-date-in-calculator-plan.md`.

- [x] **5. CIG cannot edit or send an application back to Committee after CSA corrections** — **1–2 days**
  - **Context:** The client says CSA can edit an application returned by Committee. After CSA forwards it to CIG, CIG reportedly finds the application locked and sees no button to send it back to Committee. (Image 2)
  - **Check:** Follow the full route from Committee to CSA to CIG. Check whether CIG can edit and send the application back to Committee.
  - **Assessment notes:** Audited, reproduced and **fixed (uncommitted, no database change).** On dev application AN300024 (Committee → CSA → CSA "Endorse to CIG" → CIG): the file was For Verification and CIG's fields were enabled (not fully locked), but the page showed "With Committee — Verification is complete" and "Forwarded to Committee", and the "Submit CI report to Committee" button was missing; the server would also have refused it ("CI report already submitted"). Root cause: `verifications.forwarded_at` from CIG's first submission is never reset, and CSA cannot write that table, so a re-endorsed file still looked submitted. Fix: new helper `isVerificationForwarded` (`src/lib/cig/workspace.ts`) treats a file as forwarded only if `forwarded_at` is not older than the latest `endorsed_at`; used in `src/lib/cig/forward.ts` and the CIG page. `forwarded_at` is never rewritten, so history and Committee screens are unchanged. Verified on AN300024: banners gone, badge "Forward ready", Submit button enabled, an edit persisted, and submitting moved the file to For Approval with a fresh forwarded time. CIG unit tests: 180 pass. Not verified in the browser: the normal first-pass flow and the #4 return straight to CIG (covered by unit tests), and the Committee screen's view of the new time. Open points: CSA's "Revision complete" still sends the file straight to Committee and skips CIG, so the client should confirm whether every CSA return must go through CIG; the CSA-routed return notice stays unresolved after the endorse (no visible effect found). Plan: `docs/revision-plans/fix-cig-resubmit-after-csa-correction-plan.md`.

Committee unit tests: 59 pass, 2 fail; the same 2 email-builder tests fail without this change. Plan: `docs/revision-plans/fix-committee-return-before-vote-plan.md`. Not checked: the CSA screen showing the notice, the CIG route, a held file, and Approve/Deny/Hold in the browser. Open points: votes already cast are not cleared after a return (existing behavior), and the client should confirm they want early returns.
