# Module History / Closed-Records Pages — Progress Tracker

Source: UI/UX audit session, 2026-08-11. CSA and Committee (and several other staff portals) have no way to look back at applications/accounts once they leave the active queue — only CIG (`cig/history`) and Collector (`collector/history`, DCR/payments only) have any form of this today. Design direction approved 2026-08-11: KPI quick-filter cards, collapsible Filters panel with date-range picker (presets + custom), search, sortable table, list/grid/compact view modes, and page-size pagination. Working draft: `design/LoanStar Design System/reference/drafts/history-list-pattern.html`.

## Workflow (read every time before touching this file)

0. **Audit phase first, always.** Before writing (or revising) a module's implementation plan, Claude audits the live codebase for that module — evidence-only, file:line citations, "NOT FOUND" if genuinely absent, no assuming prior memory/notes still reflect current code.
1. Claude writes a **surgical-mode** implementation plan for the module, built on the audit findings: sidebar entry, new permission-gated API route, page component matching the approved draft design, **plus a redesign phase for that module's original active-queue page** (see standing requirement below). **One `.md` file per module**, all phases (backend route, sidebar wiring, history page/UI, tests, active-queue redesign) as sequential sections in the same file.
2. The user runs the plan **through Cursor**, phase at a time — Cursor does the actual code implementation, not Claude.
3. Cursor outputs a summary of what it changed for that phase.
4. The user pastes that summary back to Claude, who **validates** it against that phase's section of the plan before moving to the next phase.
5. **After all phases in a module's file are implemented, Cursor produces one final combined summary** covering every phase for that module. The user sends this to Claude for a final end-to-end validation pass before the module is marked Done.
6. This tracker's Status/Notes columns get updated as phases are validated and land, with Notes linking to the module's plan file.

Claude should not implement code for these items directly unless the user explicitly says otherwise in a given session.

## Standing requirement: every module gets an `N.1` queue-redesign line

Added 2026-08-11. Each module in the table below has two tracked deliverables, both living in the **same** per-module plan file:
- **`N`** — the new read-only History/Closed-records page (the original ask).
- **`N.1`** — a phase in that same plan file that redesigns the module's **existing active-queue page** to match: collapsible Filters panel, date-range filter (default **"All time"**, not "Last 30 days" — an active queue must not hide old-but-still-open items by default), `ViewModeToggle` (list/grid/compact), page-size pagination. Reuses the exact shared components/CSS from `N`'s Phase 1 (or, for modules after CSA, from CSA's Phase 1 — no new shared components needed). Do **not** restyle existing icon-based KPI cards to match History's plain style unless a module's audit finds a specific reason to — see the CSA precedent (`history-plans/csa-application-history.md`, Phase 6): keep icons, add the missing pieces.

`N.1` is always the **last** phase in a module's plan file (after backend/sidebar/page/tests for `N`), since it depends on nothing new besides what `N`'s own phases already built.

## Standing requirement: every History page row/card gets a "View" action

Added 2026-08-11. Every module's History page (`N`, not `N.1`) needs a **View** button per row (list/compact table: an unsortable trailing "Actions" column; grid: a button at the bottom of the `.gcard`, same placement as the active-queue redesign's grid cards) that links to that record's **existing, original detail page** — e.g. CSA → `/csa/applications/[id]`, Committee → `/committee/applications/[id]`, LRA → `/lra/applications/[id]`, Agent → `/agent/leads/[id]`. Use `next/link` + the shared `Button` (`variant="secondary" size="sm"`, matching the exact pattern already used for the "Open" button on every active-queue page).

**Before wiring this for a given module, confirm the target detail page doesn't hard-block a non-active-queue status** (redirect/`notFound`/etc.) — CSA's `/csa/applications/[id]` was checked and is safe (`isCsaEditableStatus` just toggles an `editable` flag that hides edit affordances, no guard blocking read access). Don't assume every module's detail page behaves the same without checking that module's own audit.

If a module's History rows don't map to any single existing detail page (e.g. AR's Posting History mixes DCR references and masterlist accounts — two different targets), route the View button per-row-type, or flag it as a decision for the user rather than guessing.

## Standing requirement: search/filter/sort/pagination must be server-side, not client-side-on-a-bulk-fetch

Added 2026-08-11. **Applies to both `N` (History) and `N.1` (active-queue) pages for every module** — not History-only. CSA's retrofit covers both: Phases 8–9 for `/csa/history` (`N`), Phases 10–11 for `/csa` (`N.1`). Every module's plan from Committee onward must build both pages server-side-driven from the start — this is now part of what `N` and `N.1` mean in the two standing requirements above, not a separate add-on step. **User decision: retrofit CSA now** (`history-plans/csa-application-history.md`, Phases 8–12) rather than leave it client-side.

**The problem with the pattern used through CSA Phase 1–7**: the API returns up to `limit` rows (e.g. 200) in one shot, and the page does search/status/date-range filtering, sorting, and pagination entirely in the browser with `useMemo`. Fine at small volumes, but it means the full dataset ships to the browser on every load regardless of what's actually being viewed, and it doesn't scale as a module's row count grows.

**The fix — API routes become query-param-driven**, e.g.:
`GET /api/csa/history?search=&status=all|<group>&range=30d|90d|all|custom&from=&to=&sortKey=&sortDir=&page=1&pageSize=10`
returning `{ rows, totalCount, kpi: { total, <group1>, <group2>, ... } }` — filtering/sorting/counting done in the Supabase query itself (`.eq`/`.in`/`.gte`/`.lte`/`.order`/`.range`, `{ count: "exact" }` — same primitive `admin/audit/route.ts` already uses for offset/limit pagination), not in JS after fetch.

**Search across a joined table (e.g. borrower name/email) is the trickiest part** — PostgREST's embedded-column `.or()` filtering is fragile/version-dependent. The pattern to use instead (avoids a new RPC/migration): **two queries**. (1) If a search term is present, query the joined table alone (e.g. `borrowers`) with a plain same-table `.or("first_name.ilike...,last_name.ilike...,email.ilike...,borrower_no.ilike...")` to get matching ids. (2) Build the main query with `.or(\`application_no.ilike.%term%,borrower_id.in.(${ids.join(",")})\`)` combined with the other filters. Both queries are simple same-table filters — no embedded-join fragility, no new SQL.

**Sorting by a field that lives in a separate, non-1:1-joined table** (e.g. CSA History's "Amount"/"Loan Type", sourced from `computations` and batch-fetched per page) is **not** worth forcing fully server-side — sort that field client-side on just the current page's already-fetched rows (10–100 rows, cheap) while every other sort key (fields that live on the base table, or a single embedded-order-by like borrower name) sorts server-side via `.order()`. State this scoping explicitly in each module's plan rather than silently picking one.

**KPI counts** (which must stay scoped to the date range only, not the status filter, per the existing History design) become a small number of cheap `head: true` count-only queries — one per KPI card — rather than counting an in-memory array.

**Frontend**: replace the one-time fetch + `useMemo` filter chain with: page/filter/sort state changes trigger a re-fetch with the new query params (debounce the search input, ~300ms, to avoid a request per keystroke).

## Standing requirement: loading state uses `Skeleton`, not a full-page `Spinner`

Added 2026-08-11. Applies to both `N` and `N.1` pages, system-wide going forward (not just this rollout). The existing `Skeleton` component (`src/components/ui/Skeleton.tsx`) already has `kpi` and `list-row` variants — reuse them, don't invent new loading UI per page.

**The problem with `if (!hasLoaded && loading) return <Spinner />`**: it blanks the *entire* page (including `PageHeader`, toolbar, and filters, none of which depend on fetched data) until the first response lands — a jarring blank-then-content flash.

**The fix**: always render the full static page shell immediately (title, description, toolbar, search box, filter panel — all data-independent). Only the data-dependent regions render skeletons **whenever `loading` is true — not just the initial load**:
- **Applies to every refetch, not only first paint**: the debounced search firing, changing a status/date-range filter, clicking a KPI quick-filter, sorting a column, changing page or page size — every one of these sets `loading` back to `true` while the new response is in flight, and the skeleton should reappear each time, exactly like the first load. Gate on `loading` alone, not `!hasLoaded && loading` — the "only skeleton the very first load" carve-out from this rule's original version is retracted, per user correction 2026-08-11.
- **KPI row**: render `<Skeleton variant="kpi" />` once per KPI card slot (same count/grid as the real cards) instead of the real `Kpi`/stat buttons, whenever `loading`.
- **Table/grid body**: render ~6 skeleton rows instead of real rows — inside the real `<Table>` (so the header stays visible), each row as `<tr><Td colSpan={<column count>}><Skeleton variant="line" /></Td></tr>`, or `<Skeleton variant="list-row" />` repeated if a module's row shape fits that variant better — whenever `loading`.
- **Empty-state checks must not fire while `loading`** — gate them the same way (e.g. `loading ? <skeleton> : totalCount === 0 ? <EmptyState/> : <realContent/>`), so a page never flashes "No matching records" using stale/zeroed data while a request is in flight, on first load or any refetch.
- If a page's `loading`/`hasLoaded` state pair becomes redundant once `hasLoaded` is no longer needed for this gating, simplify to just `loading` rather than leaving a now-pointless second flag — but check `hasLoaded` isn't used for anything else on that page first.
