# Item 10 — Combine signing documents into one upload (step-by-step)

Part of the System Revision Report rollout. See `loanstar/docs/system-revision-report-tracker.md` for the workflow rules and overall status.

**Tracker item:** *Instead of uploading each signing document one at a time, staff should be able to combine all of them into a single file and upload it once, with one confirmation step.*

**Scope, confirmed with the user via screenshot 2026-08-11:** this covers **both** checklist cards on the LRA release page that are genuine file-upload slots — "Signing-stage uploads" (Affidavit of Understanding + Bank Authorization on the `with_pdc` path; ATM Authorization on the `without_pdc` path) **and** "Release checklist" (Signed Check Voucher, Release Transmittal, Signed Promissory Note, Signed Disclosure Statement — same 4 for both paths). These get **replaced** by a single combined upload + one confirmation. The separate "Generated documents" panel (Blri, Check Voucher, Promissory Note, etc. — the 7 "Mark signed" click-to-confirm buttons, no file upload involved) is explicitly **not** part of this item — confirmed out of scope by the user.

### Scope decision

### Files to change

1. **New file: `src/lib/lra/combined-signing-upload.ts`**
   - Export a pure helper (unit-testable without a DB):
     ```ts
     import { isAutoGeneratedDocumentSlug } from "./constants";
     import type { ChecklistItem } from "@/lib/documents/checklist";

     export type CombinedUploadTarget = {
       documentTypeId: string;
       documentTypeSlug: string;
       documentTypeName: string;
     };

     /**
      * Required, non-auto-generated document types across the signing-stage
      * card (auto-generated PDFs excluded, same as the frontend's
      * excludeSlugs) and the release checklist card (no exclusions) — the
      * exact set the combined upload satisfies in one shot.
      */
     export function resolveCombinedUploadTargets(
       signingStageItems: ChecklistItem[],
       releaseItems: ChecklistItem[],
     ): CombinedUploadTarget[] {
       const targets = new Map<string, CombinedUploadTarget>();
       for (const item of signingStageItems) {
         if (!item.isRequired) continue;
         if (isAutoGeneratedDocumentSlug(item.documentTypeSlug)) continue;
         targets.set(item.documentTypeId, {
           documentTypeId: item.documentTypeId,
           documentTypeSlug: item.documentTypeSlug,
           documentTypeName: item.documentTypeName,
         });
       }
       for (const item of releaseItems) {
         if (!item.isRequired) continue;
         targets.set(item.documentTypeId, {
           documentTypeId: item.documentTypeId,
           documentTypeSlug: item.documentTypeSlug,
           documentTypeName: item.documentTypeName,
         });
       }
       return Array.from(targets.values());
     }
     ```
   - Deduping by `documentTypeId` via `Map` is deliberate — if a slug were ever required in both stages (not the case today), it should still only be written once.

     5. Call `resolveCombinedUploadTargets(signingItems, releaseItems)`.
     6. ## Phase 4 — Migration: combined-upload log table

User-requested extension 2026-08-11: add optional remarks at upload time, a way to view the uploaded file, and a persistent record of who uploaded it and when (not just an in-session UI message that disappears on reload).

### Audit findings (evidence, verified 2026-08-11, live DB `acopcwlhkovssjnrqygk`)

- `documents` table has no free-text field suitable for this — it has `revision_remarks`, but that column is semantically for CSA's "needs revision" rejection reason (written by `requestRevisionApiPath` flows across the app, e.g. `DocumentChecklist.tsx`'s `handleRequestRevision`). Reusing it here would collide with that existing meaning and could confuse/break the unrelated revision-request feature. **Do not reuse `revision_remarks`.**
- The combined upload writes **6 separate `documents` rows** (one per satisfied document type, per Phase 1) all pointing at the same `storage_path` — there's no single row that represents "the one combined upload event." Storing remarks/uploader/timestamp per-document-row would mean picking one arbitrarily as "canonical," which is fragile and confusing. A dedicated one-row-per-combined-upload log table is the correct shape.
- `documents` RLS policies for the `release_lra` module (confirmed live via `pg_policies`): `documents_lra_insert` → `WITH CHECK (has_module_permission('release_lra','edit'))`; `documents_lra_select` → `USING (has_module_permission('release_lra','view'))`. Mirror this exact pattern for the new table — no `is_super_admin()` OR-clause needed since that's not present on these two specific existing LRA policies either (unlike some other tables' policies) and super-admin already satisfies `has_module_permission` universally in this app's permission model.
- Existing "view a document" mechanism (`/api/documents/[id]/download`, already used by `DocumentChecklist.handleView` and referenced via `viewApiPath` throughout this codebase) works off a `documents.id` — no new view mechanism needs to be built; the log table just needs to retain at least one of the 6 `documents.id` values so the frontend can call the existing route.

### Change to make

New migration:

```sql
CREATE TABLE lra_combined_signing_uploads (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  loan_application_id uuid NOT NULL REFERENCES loan_applications(id) ON DELETE CASCADE,
  storage_path text NOT NULL,
  file_name text NOT NULL,
  mime_type text NOT NULL,
  file_size bigint NOT NULL,
  remarks text,
  document_ids uuid[] NOT NULL,
  uploaded_by uuid NOT NULL REFERENCES auth.users(id),
  uploaded_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX lra_combined_signing_uploads_app_idx
  ON lra_combined_signing_uploads (loan_application_id, uploaded_at DESC);

ALTER TABLE lra_combined_signing_uploads ENABLE ROW LEVEL SECURITY;

CREATE POLICY lra_combined_signing_uploads_insert ON lra_combined_signing_uploads
  FOR INSERT TO authenticated
  WITH CHECK (has_module_permission('release_lra', 'edit'));

CREATE POLICY lra_combined_signing_uploads_select ON lra_combined_signing_uploads
  FOR SELECT TO authenticated
  USING (has_module_permission('release_lra', 'view'));
```

Apply via Supabase MCP, written to **both** `supabase/migrations/` and `loanstar/supabase/migrations/` — not `supabase db push`.

- `documents` table / `revision_remarks` column — untouched, not reused.
- No changes to any existing table's RLS.
- No application code in this phase — schema only.
